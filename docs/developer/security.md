# Security Implementation

This page describes how the gateway and the admin service handle keys, credentials, authentication and security events. How an operator sets the keys is described in [Docker Compose](/deploy/docker#security-keys) and [SAP BTP Kyma](/deploy/kyma); the roles in [Roles](/guide/roles).

## Cryptographic Key Management

### The security keys

| Variable | Used by | Purpose |
|---|---|---|
| `VALIDATION_TOKEN_SECRET` | gateway and admin (same value) | signs the gateway's service JWT (HS256, issuer `gateway-service`, `services/gateway/src/clients/adminServiceClient.ts`) and the validation tokens of `libs/aws-token-validation/validation-token.ts` |
| `METADATA_ENCRYPTION_KEY` | gateway | encrypts credential metadata in the gateway's validation cache (`libs/aws-token-validation/secure-metadata-exchange.ts`, AES-256-CBC with a PBKDF2-derived key); falls back to `VALIDATION_TOKEN_SECRET` and, without either, to a development key that throws under `NODE_ENV=production` |
| `AWS_SECRET_ENCRYPTION_KEY` | admin | encrypts the stored secret access keys of AWS credentials (`services/admin/src/utils/awsSecretCrypto.ts`: AES-256-CBC, key derived with scrypt, stored as `iv:ciphertext` in hex) |
| `SIEM_CREDENTIAL_KEY` | admin | encrypts the stored SIEM sink credentials (see [Pseudonymization security assessment](/developer/pseudonymization-assessment#_12-4-sink-credential-storage)) |
| `CONNECTION_CREDENTIAL_KEY` | admin | encrypts the stored Connection credentials (see [Connections internals](/developer/connections#credentials)) |

**Publicly known values are refused or reported.** Outside `NODE_ENV=development`, a `VALIDATION_TOKEN_SECRET` that is unset, the built-in default or the `.env.sample` placeholder is refused: the admin accepts no gateway service JWT signed with it and hands out no AWS signing keys, and logs one error (`services/admin/src/utils/gatewayServiceJwt.ts`, list in `libs/aws-token-validation/validation-token-secrets.ts`).

Unset, the admin encrypts stored AWS secrets with a built-in development key. A deployed admin
(`NODE_ENV=production`, or `DEPLOY_TARGET` docker, xsuaa, btp or xsa) whose key is unset or the
`services/admin/.env.sample` value logs a `SECURITY WARNING` at startup and keeps running
(`warnIfAwsSecretKeyIsPubliclyKnown` in `services/admin/src/utils/awsSecretCrypto.ts`); the key is never
logged. After setting a new key, the stored AWS secrets must be entered again: the old ciphertexts do not
decrypt under it.

Generate each key as 32 random bytes in hex, for example with `openssl rand -hex 32` or:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

The Docker and Kyma setups generate them. Keep them with the backups: data encrypted under a key cannot be read without it.

## Authentication Systems

### API keys

Gateway API keys are `sk-` followed by random hex (`services/admin/src/srv/admin-service.ts`): 64 hex characters (`crypto.randomBytes(32)`) when a key is created in the cockpit and after a rotation, 48 (`crypto.randomBytes(24)`) when it is created through the admin OData action `createApiKey`. The admin stores the key itself, not a hash, in `ApiKeys.key` (`services/admin/src/db/schema/api-keys.cds`). Where a client may send the key is listed in [API authentication](/reference/authentication).

The gateway validates a key with the admin's unified validation (`validateUnifiedAuthByToken`) and caches the answer (`unifiedValidationCache.ts`, Valkey when available); a key that is inactive, expired or unknown is refused with `401`. Without an admin (the standalone CLI), the gateway validates against its local credential store.

### AWS credentials and Signature V4

An AWS credential is an access key id (`AKIA` followed by 16 uppercase hex characters) and a 40-character hex secret access key, generated by the admin. The admin stores the secret encrypted with `AWS_SECRET_ENCRYPTION_KEY` and never returns it to the gateway.

The gateway verifies every SigV4 request itself (`services/gateway/src/utils/sigv4Verifier.ts`). It accepts a request date within 15 minutes of its clock, tries the host and path variants a request may have been signed with (the Host header with and without port, the original Bedrock hosts, the path with and without the `/aws-bedrock` mount, and behind nginx the path under the `/gateway` prefix, the only forwarded prefix it accepts), and the `bedrock` ↔ `bedrock-runtime` service variant. The payload hash is always computed from the body the gateway received: a declared `x-amz-content-sha256` other than that hash (`UNSIGNED-PAYLOAD` and `STREAMING-*` included) fails, and so does a body the gateway did not capture, which is why multipart routes answer `403` to AWS credentials. Signatures are compared in constant time, and nothing in the verifier logs a key, a signature or the `Authorization` header.

**Signing-key contract (gateway ↔ admin)**: the gateway verifies every SigV4 request itself
(`services/gateway/src/utils/sigv4Verifier.ts`), and the admin never returns an AWS secret. For
an AWS credential, `createUnifiedValidationToken` takes
`signingScopes: [{ date, region, service }]` — the scope from the request's `Authorization`
header plus the `bedrock` ↔ `bedrock-runtime` variant the verifier also tries (at most 4).
`validateUnifiedAuthByToken` then answers with
`data.signingKeys: [{ date, region, service, key }]`, where `key` is hex(kSigning) derived the AWS
way from the decrypted stored secret: kDate = HMAC("AWS4" + secret, date), kRegion, kService,
kSigning = HMAC(kService, "aws4_request").

- **Who gets keys** (`services/admin/src/utils/gatewayServiceJwt.ts`): only a request whose
  `Authorization` is the gateway's service JWT (`Bearer`, HS256 under `VALIDATION_TOKEN_SECRET`,
  issuer `gateway-service`), in every deploy target. Outside `NODE_ENV=development`, an unset or
  default secret issues no keys, and the admin logs one error. Any other caller gets the validation
  answer without `signingKeys`. nginx blanks client-sent `X-Auth-Request-*` headers on
  `/admin/odata/v4/validation/`.
- **Admin checks** (`services/admin/src/services/awsSigningKeys.ts`): the whole validation is
  refused with `INVALID_SIGNING_SCOPE` in three cases:
  - more than 4 scopes;
  - a date that is not a real `YYYYMMDD` day, or is not the UTC day of now ± 15 minutes (the
    gateway's `x-amz-date` skew);
  - a region or service outside `^[a-z0-9-]{1,32}$`.

  A stored secret that cannot be decrypted with `AWS_SECRET_ENCRYPTION_KEY` fails with
  `SIGNING_KEY_UNAVAILABLE`.
- **Admin caching**: the admin's validation cache holds the result without keys. Keys are derived
  per request from the stored secret, so a cache hit re-reads the row. The row must be active and
  not expired (an expired row is auto-locked).
- **Refused credentials that exist** (both credential types): when `validateUnifiedAuthByToken`
  refuses an API key or access key id whose row exists but is inactive or expired, the invalid
  answer carries that row's ID in `error.credentialId` — for the gateway's service JWT only, never
  for an unknown key. The gateway puts it into the `failed_auth` security event as `credentialId`
  (plus `credentialHint`, `resolvedCredentialIdentity` in `utils/credentialIdentity.ts`), so the
  admin links the event to the credential and notifies its owner; a SigV4 signature or payload
  failure for a resolved credential does the same. The client's 401/403 body never contains it.
- **Gateway caching**: the gateway keeps the keys in process memory only
  (`services/gateway/src/services/awsSigningKeyCache.ts`). They are keyed by access key id and
  scope, and dropped once the scope date is more than a day old. The unified validation cache
  (Valkey) strips `signingKeys` like it strips `secretAccessKey`.
- **Key misses**: when a validation-cache hit finds no key in memory (another replica, a new day),
  the admin signing-key provider asks the admin once for the scope and its variant.
- **Key source**: a result validated from the gateway's local credential store (standalone mode,
  or the local fallback during an admin outage) records `keySource: 'local'` in its cache entry.
  A cache hit is therefore verified with the local key again, never with the admin's.

## Authorization

The admin service knows two roles, `admin` and `user`; what each may do is described in [Roles](/guide/roles). The admin entities and actions of `services/admin/src/srv/admin-service.cds` declare `@(requires: 'admin')` where only administrators may act; ownership rules for credentials are enforced in the handlers (see the lifecycle rules below). The gateway does not authorize by role: it authenticates the credential and then applies the owner's entitlements, quotas and tool policies.

### Credential Lifecycle

API keys and AWS credentials share one set of lifecycle rules, held as pure functions in
`services/admin/src/services/credentialLifecycle.ts` so they are unit-testable without a server.

**Admin-only fields.** `isActive`, `expiresAt` and `neverExpires` may only be changed by an
administrator — not by the credential's owner. `lifecycleChangeViolation()` compares the incoming
payload against the stored row and is enforced in `beforeUpdateApiKeyActive` /
`beforeUpdateAwsCredentialsActive`. Draft activation resends the whole row, so a value equal to the
stored one is not treated as a change. The Fiori apps get matching field control (`isActiveFC` /
`expiresAtFC` / `neverExpiresFC`) from the after-READ handler, so they never provoke the 403. A
non-admin's draft edit of any of the three is dropped in the `.drafts` before-UPDATE handler, so
activation carries the stored values through unchanged — which is the path the apps actually take,
since lean draft answers a direct PATCH of an active row with 501 before any handler runs.

**Preset on create.** `before('NEW', '<Entity>.drafts')` prefills a create draft with
`expiresAt = now + the configured period`, plus `neverExpires = false`, `isActive`, `usageCount`
and — for a non-admin — the caller's own identity. It must be registered on the *draft* entity with `before`: an
`on('NEW', '<Entity>')` handler never fires under lean draft, which is why Expires At used to come
back empty.

**No past dates.** `expiresAtInPast()` guards every write path — both create handlers, the
`createAwsCredentials` action, and both update handlers (after the admin-only guard, and only when
the value actually differs from the stored one, so a row that is already past its date stays
editable). Rejection is `400 Expires At must be in the future`. The guard is skipped when the write
leaves the credential flagged `neverExpires`, since such a row stores no date at all.

**A refresh extends.** `rotationPolicy()` returns a fresh `expiresAt` for every permitted rotation,
owner or administrator alike — a refresh always moves the date forward, except on a credential
flagged `neverExpires`, which is returned `expiresAt: null` so the refresh does not quietly
reintroduce an expiration the flag exists to suppress. An owner is still refused
on an inactive or already-expired credential (`{ allowed: false, reason: 'inactive' | 'expired' }`),
so a refresh can extend a live credential but never resurrect a dead one. This resurrection differs
by entity: an administrator can rotate an inactive or expired API key directly (`rotateApiKey` reads
the row regardless of `isActive`, and `rotationPolicy()` then allows the admin case). AWS credentials
go further — `rotateAwsCredentials` looks the row up filtered on `isActive = true`, so an inactive
credential is refused before `rotationPolicy()` is even reached; an administrator must re-enable it
first, then rotate it.

**Enforcement.** `credentialExpired(row)` is checked on every validation path — `validateApiKey`, the unified
`validateUnifiedAuthByToken` for both credential types, and the legacy
`validateAwsCredentialsByToken` — each of which rejects the credential and auto-locks it
(`isActive = false`) so a lapsed credential stops being presented rather than failing open. In
practice this means an expired credential is rejected the next time it is presented on any of these
routes once any cached validation result for it has lapsed (a few minutes at most); an
administrator's `isActive`/`expiresAt` change takes effect immediately, since the handlers that make
it (disable/enable/rotate) broadcast a cache invalidation of their own rather than waiting on a
validation call to discover the new state. The auto-lock itself is idempotent: only the request that
actually flips the row clears the caches and broadcasts the invalidation, so a repeatedly presented
expired credential does not re-broadcast. Adding a validation path means adding this check to it.
`expiresAt = null` still means "never expires", so a row that somehow has neither is not rejected.

**The never-expires flag.** `neverExpires` is an admin-only Boolean on both entities that makes
"this credential does not expire" an explicit, stored property instead of an implicit null date.
`credentialExpired(row)` short-circuits to `false` when it is set, so a flagged row is valid on
every validation path even if it still carries a stale date from before it was flagged, and it is
excluded from the `ExpiredAwsCredentials` view and admitted by `ActiveApiKeys`. `normalizeLifecycle()`
keeps the pair consistent on every write: setting the flag clears `expiresAt`, and clearing it
without supplying a date assigns the standard period rather than leaving the credential dateless.
`afterReadLifecycleFieldControl` reports `expiresAtFC = 1` (read-only) on a flagged row for every
role — on AWS credentials the field is otherwise `7` (Mandatory) for administrators, which would
leave the object page demanding a value the flag suppresses.

Rows that predate the column are migrated once, at admin startup:
`backfillNeverExpires()` (`src/db/data/never-expires-backfill.ts`, invoked from
`initializeNeverExpiresBackfill` beside the SapCapacityUnitPrice seed) flags every API key and AWS
credential with no `expiresAt`. It is idempotent — the `WHERE` clause matches nothing on a second
run — so it is safe on every boot and on every target: Postgres gets the column itself from
`schema_evolution: auto`, and a local SQLite dev database gets it from the admin's boot-time
self-heal (`services/admin/src/db/data/sqlite-schema-heal.ts`), which adds missing nullable or
defaulted columns.

**Configuration.** One platform parameter, `platform.security.credentialExpirationDays`, governs
both credential types on creation and on refresh. It defaults to 90 days and falls back to 90 when
absent or not an integer >= 1. Note that `api_config.json` is byte-identical between
`services/admin` and `services/gateway`; change both.

**Admin detection.** `isAdmin()` matches a role exactly (`admin`, `Admin`) or as an xsuaa scope
suffix (`.admin`). The substring match it used to do would let a scope such as `non-admin` or
`admin-readonly` pass the admin-only lifecycle guards. On Kyma this means a scope must be named so
that it ends in `.admin` to grant administrator rights — a bare custom scope name that merely
contains "admin" no longer qualifies.

## Pseudonymization

The pseudonymization plugin masks personal data and secrets in outbound requests and restores them in responses. Its detection tiers, operating modes, evidence and residual risks are documented in [Pseudonymization security assessment](/developer/pseudonymization-assessment); how it is hooked into the request pipeline in [Plugin system](/developer/plugins). A response that contains a placeholder the model was never sent raises a `placeholder_invented` security event.

## Security Events and Monitoring

### Security Event Types

The event types are those of `SecurityEventType` in `services/gateway/src/types/security.ts`; the admin accepts the same list (`services/admin/src/srv/admin-service.ts`):

| Type | Raised when |
|---|---|
| `failed_auth` | a credential is refused (unknown, inactive or expired key, wrong signature, missing or stale request date) |
| `credential_rotation` | a credential is rotated (recorded by the admin, not the gateway) |
| `model_not_entitled` | the caller requests a model outside its entitlements |
| `tool_not_entitled` | a tool policy strips or rejects tools in `strip` or `reject` mode |
| `deployment_created` | a deployment is created through the gateway's deployment route (with a service key) |
| `quota_exceeded` | a request is refused with `429` by a rate limit or quota |
| `quota_unenforced` | quotas cannot be enforced because Valkey is unreachable (throttled) |
| `placeholder_invented` | a response carries a pseudonymization placeholder the model was never sent |

Each event carries a severity (`low`, `medium`, `high`, `critical`), the action taken (`logged`, `blocked`, `throttled`, `monitored`, `alerted`, `quarantined`), the credential and its type, and request context (client IP, user agent, endpoint, method, request ID). `SecurityEventEmitter` (`services/gateway/src/services/securityEventEmitter.ts`) publishes them to a Valkey stream; without Valkey, or when publishing fails, it queues them in memory and flushes them to the admin service. A security event never fails the request it describes. The admin stores them as security notifications ([Security notifications](/guide/cockpit/security-notifications)) and can export them to a SIEM.

**Client-IP trust.** Every event's `ipAddress` goes through one derivation
(`services/gateway/src/utils/clientIp.ts`), gated by the `platform.security.trust_forwarded_for` setting
(default `false`). On Docker, nginx sets `X-Real-IP` and appends the real peer to
`X-Forwarded-For`, so `trust_forwarded_for: true` yields the real caller address. On Kyma, the
Istio ingress appends to `X-Forwarded-For` and may not set `X-Real-IP`, so the last hop of that
header is used instead. With the shipped default of `false`, the socket peer — the proxy in front
of the gateway, not the caller — is recorded, on purpose: an unconditionally trusted forwarding
header would let any client dictate the IP recorded against its own security events. IPv4-mapped
IPv6 addresses (`::ffff:203.0.113.7`) are normalised to their IPv4 form. The IP is personal data
and is written only into security and audit events.

## Rate Limiting and Quota Enforcement

Rate limiting is not adaptive or reputation-based: it is the fixed, per-key and per-user
enforcement in `quotaEnforcement` (`services/gateway/src/middlewares/quotaEnforcement.ts`) — see
[Quota enforcement](/developer/gateway#quota-enforcement) for the full mechanism. In short:
Valkey-backed requests-per-minute/hour/day counters per credential and per user
(`rl:key:<id>:*`, `rl:user:<sha256(email)>:*`), spend and token admission per day/week/month
against the per-user state document the admin publishes (`quota:user:<sha256(email)>`), a `429`
naming the scope, dimension, window, limit, usage and reset time, and fail-open to per-pod memory
counters — with a throttled `quota_unenforced` security event — when Valkey is unreachable.
Standalone mode (no admin configured) falls back to an in-memory per-key requests-per-minute limit
only (`RATE_LIMIT_RPM`), with no user scope. There is no separate DDoS-specific layer: these
per-key and per-user limits are what bound request volume from any one caller.

## Secure Communication

The bundled nginx serves HTTP only; TLS is terminated by a reverse proxy or load balancer in front of it on Docker ([Docker Compose](/deploy/docker#production)) and by the Istio ingress on Kyma ([SAP BTP Kyma](/deploy/kyma)). Inside the Docker network the services talk over plain HTTP; the internal ports are bound to `127.0.0.1`.
