# Changelog

Notable changes to SAIL-PROXY. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and the project uses [Semantic Versioning](https://semver.org/). Changes waiting for the next release are
listed under **Unreleased**; at release time that heading becomes the version and its date.

## [0.11.0] - 2026-10-29

### Security

- The Docker and Kyma nginx no longer signs anyone in to the Admin Cockpit or the admin API with a bearer token. Its token check could not verify signatures, so it accepted a token without a valid signature. Every admin route now asks oauth2-proxy for the session. API keys on `/gateway/` routes and the gateway's service token for calls inside the cluster are unchanged. The nginx image no longer contains the njs module, and nginx no longer reads `JWT_ISSUER_URL`, `JWT_AUDIENCE`, `JWKS_ENDPOINT` or `ENABLE_JWKS_CACHE`. Rebuild and redeploy the nginx image.
- AWS SigV4 signatures are now verified; before, they were not. AWS clients must sign with the credential's real secret access key.
- AWS SigV4 authentication works on JSON routes only. Multipart routes, such as file upload and image edits, answer 403 to AWS credentials.
- AWS clients behind the Docker nginx may sign for the `/gateway` path; no other forwarded path prefix is accepted.
- A failed sign-in with a known API key or AWS access key id is linked to that credential and its owner is notified. This covers a wrong signature, a disabled or expired key, and a request whose date is missing or too old (for example, a replayed one).
- SIEM security events for a known credential carry the credential's ID as `credential_id` instead of a hash. Unknown credentials keep the hash.
- Outside development, the admin refuses every gateway service token signed with a publicly known `VALIDATION_TOKEN_SECRET` (the built-in default or the `.env.sample` placeholder), everywhere it checks one.
- Forced pseudonymization now holds on every chat route. A forced request is masked or refused: the gateway refuses it when the plugin cannot run (NER unavailable, a body it cannot read, the force flags unreadable, a pseudonymization error) and when the plugin never saw it. This covers deployed and OpenRouter chat, orchestration, Bedrock Converse and Nova bodies, Bedrock models served through orchestration, and Gemini and Converse tool history. Tool-call arguments in the history are masked too. Embeddings, file and grounding contents and SAP-RPT are not pseudonymized.
- API keys in URLs, key headers and referers are masked in the gateway's access log, debug lines and security events, in payload logs and in the nginx access log. The Ollama facade logs neither the gateway key nor the conversation.
- The emulated Bedrock Converse stream no longer evaluates upstream data as JavaScript.
- Invalid `masking.custom_entities` entries, including unsupported regex flags, are dropped and logged instead of disabling masking for the whole request.
- The Admin Cockpit refuses API keys and AWS credentials for e-mail addresses reserved for platform service keys.
- The admin logs a security warning at startup outside development when `AWS_SECRET_ENCRYPTION_KEY` is missing or still the built-in development or sample value: the AWS secret access keys it stores are then encrypted with a publicly known key. It still starts, so existing installations keep working. Set a generated key and enter the stored AWS secret access keys again (see the installation chapter).

### Billing

- Connection usage is priced from the list price in force at the request, per 1K tokens, in the price's currency (which defaults to the installation currency), and shown apart from SAP cost: a **Connections cost** tile on the home page, a KPI and a spend-per-connection table in Usage Analytics. Spend quotas count SAP cost plus Connection cost in the quota currency. SAP billing, reconciliation and the SAP cost tile are unchanged. Connection usage is booked even while SAP AI Core's model list is unavailable.
- Bedrock usage is no longer dropped after the first batch.
- A gateway without Valkey, or whose Valkey is unreachable, sends its usage to the admin directly. The admin refused those batches, so that usage was lost; it is now recorded.
- Grounding usage is recorded: the embedding of files at ingestion and at re-embedding, and every search, including the Responses `file_search` tool; a search that reranks also records the rerank, in search units. Cockpit actions are booked to the acting user, ingestion and re-embedding to the store's owner, and the usage counts toward quotas. Usage Analytics shows the cockpit's own key as **Grounding cockpit (on behalf of users)**. An embedding or rerank model without a Model Library price records at zero cost. Grounding actions in the cockpit that start paid work are refused once the payer's quota is used up (see Changed). Files added before this release record nothing when they are ingested.
- Requests served through emulated or streaming fallback paths are now billed with their real token counts.
- Anthropic requests on the orchestration route, which SAP answers in Converse format, are now billed with their real token counts.
- A cache price of 0 is now honoured.
- A client that disconnects from a streaming route is recorded as status 499, with the tokens used up to that point.
- Cached prompt tokens on OpenAI-family and Gemini models were counted twice; they are now billed once. Claude and Amazon Nova, which report cached tokens separately from the rest of the prompt, were billed correctly and still are.
- The Converse-format `totalTokens` now includes cache tokens, as the usage records do; for Claude it previously left them out.
- The SAP cache billing factors for Anthropic models (`sap_cache_read_token_billing_factor` and `sap_cache_write_token_billing_factor` under `providers.anthropic`) now take effect when usage is recorded, and the daily cost recalculation applies them to Anthropic models only. Before, recording ignored them and the recalculation applied them to every model it repriced. The shipped factors are 1, so nothing changes unless you set another value. If you did, usage recorded before this release keeps its earlier SAP-native figures on PostgreSQL, because the daily recalculation only reprices rows whose dollar costs changed, and no cockpit or command-line action recomputes them yet; open a [GitHub issue](https://github.com/st-gr/sail-proxy/issues) if you need them corrected. On SQLite the next daily run reprices the last 30 days.
- Grounding records the language-model calls it makes: the contexts of contextual chunks as `file_search/context`, booked to the store's owner like the embeddings, with cache writes and reads in their own fields, and query rewriting as `file_search/rewrite`, booked to whoever searched. A context written again when a file's ingestion is retried is recorded again. A model without a Model Library price records at zero cost.
- Grounding records the page transcriptions of vector stores that use vision transcription as `file_search/vision`, one event per page (and one per model check when such a store is re-chunked or its files are read again), booked to the store's owner like the embeddings. Pages transcribed again — on a re-chunk, a **Re-read Files** job or a retried ingestion — are recorded again. The default vision model `gemini-3.5-flash-lite` is priced by SAP's catalogue in the Model Library like other models; a vision model without a price there is recorded at zero cost.

### Deployment

- The admin has a new master key, `CONNECTION_CREDENTIAL_KEY`, which encrypts stored Connection credentials. Docker and Kyma setup generate it and keep it when run again. Docker setup also adds it to an existing admin `.env` that lacks it. Kyma deploy refuses to change it once a deployment has it, like the other keys. Back it up with the other keys: a database restored without it cannot decrypt the stored connection credentials.
- Upgrade the admin and the gateway together. They must share one `VALIDATION_TOKEN_SECRET` that is neither the built-in default nor the `.env.sample` placeholder.
- Docker setup replaces a publicly known `VALIDATION_TOKEN_SECRET` found in an existing `.env` with a generated one, in both the admin and the gateway file.
- The first deploy after the upgrade drains any backlog of stuck security events on Postgres.
- Old validation-cache entries in Valkey expire within their normal lifetime; no manual flush is needed.
- Kyma: `--namespace` and a namespace prompt allow a second instance on the same cluster.
- Kyma: keys carry over between setups, with a guard at deploy time. Key rotation is not supported.
- Kyma: the custom image version accepts any valid Docker tag, verified against the registry listing when that listing is available.
- Docker: the admin, Valkey, Postgres, Dex and oauth2-proxy ports are bound to 127.0.0.1 only.
- The file search database gets a one-time schema upgrade for re-embedding on the gateway's first start. On large databases it briefly locks the chunk table: about 1.2 seconds at a million chunks. A search running at that moment can fail once and succeeds when repeated. An install whose database role does not own the file search tables reports file search as unavailable until the migration step (`cli-tools/file-search-migrate.js`, or `FILE_SEARCH_MIGRATION_DATABASE_URL`) has run as the owner.
- The file search database gets three nullable columns on `vector_store_files` (`credential_id`, `auth_type`, `on_behalf_of`) for usage recording, added on the gateway's first start by an owner install. An install whose database role does not own the file search tables reports file search as unavailable until the migrate CLI (`cli-tools/file-search-migrate.js`, or `FILE_SEARCH_MIGRATION_DATABASE_URL`) has run as the owner.
- `LOG_LEVEL` now takes effect. Before, it was ignored unless the configuration still had the old top-level `logging` block. The Docker admin image sets it to `info`, the level stock admins already logged at.
- `platform.logging.defaultLevel` and `log_folder_path` are now read as well. A stored configuration with a custom `log_folder_path` now writes its file logs there.
- Logging components that a configuration pins to a level (`platform.logging.components`) keep that level whatever `LOG_LEVEL` says. The shipped configuration pins none. A stored configuration that still lists components keeps them pinned; to have `LOG_LEVEL` govern them, create and activate a configuration without those entries.
- The admin Docker image is smaller and ships no build or test tooling. It runs on PostgreSQL only, as Docker Compose and Kyma run it; an admin container overridden to use SQLite no longer starts.
- The file search database gets the tables and columns for blob storage in S3 and for blob migrations on the gateway's first start (owner installs); existing files stay in the database, nothing is moved. An install whose database role does not own the file search tables reports file search as unavailable until the migrate CLI (`cli-tools/file-search-migrate.js`, or `FILE_SEARCH_MIGRATION_DATABASE_URL`) has run as the owner.
- Kyma: the gateway reads an optional Secret `gateway-s3-env` with the S3 credentials for file search (`kyma/templates/secrets/gateway-s3-env.yaml.template`); it starts without it, and `setup-kyma.js` carries its values over on a re-run.
- `kyma-db-manager.js` `backup` and `info` count the file search files stored in S3 and warn that a database backup does not contain their content; `restore` warns when the backup lists such files.
- The file search database gets nullable columns for structured and contextual chunks and per-store chunking (`context`, `context_tsv`, `section`, `section_offset` and `heading_path` on `vector_store_chunks`; `chunking` on `vector_stores`; `target_chunking` and four context counters on `fs_jobs`), and `vector_store_chunks.embedding` accepts NULL. These change only the catalog, no table is rewritten. An index on `context_tsv` is built afterwards, once the columns are committed: while it is built (one scan of the chunk table) writes to vector stores wait, searches are not affected. An install whose database role does not own the file search tables reports file search as unavailable until the migrate CLI (`cli-tools/file-search-migrate.js`, or `FILE_SEARCH_MIGRATION_DATABASE_URL`) has run as the owner.
- Existing vector stores keep their chunks and stay **Static (800/400)** until someone changes their chunking; nothing is re-chunked by the upgrade. An installation whose configuration was written before this release (an activated configuration on Docker or Kyma, or a standalone install's `api_config.json`) has a `capabilities.file_search.chunking` block without `strategy`; such a block stays static with its own sizes and without contexts, so the upgrade starts no language-model calls. An unset chunking key means what the Configuration form shows for it: strategy `static`, `contextual` off (overlap 400 with `static`, 0 with `structure`); a configuration without the block is static 800/400. To use the new default there, set `{"strategy": "structure", "max_chunk_size_tokens": 800, "chunk_overlap_tokens": 0, "contextual": true}` and activate the configuration. New installations, and those that use the shipped configuration file, get structure chunking with contexts (see Changed); on a standalone (npm) install, `sail-proxy config reset` rewrites `api_config.json` from the new template and so switches them on too. The default context model `gemini-3.5-flash-lite` is priced by SAP's catalogue in the Model Library like other models; a context model without a price there is recorded at zero cost. Reasoning models (gpt-5 family, o-series) are not supported as the context model. During a rolling deploy with several replicas, an old replica that ingests a file while a store is re-chunked writes static chunks into the new chunking; a later re-chunk repairs it.
- `capabilities.file_search.chunking` takes tighter ranges: `max_chunk_size_tokens` 100–4096, `chunk_overlap_tokens` 0–2048 and at most half of `max_chunk_size_tokens`. A stored configuration with a value outside them opens in the JSON editor instead of the form and is refused on save until the value is corrected; until then new stores get static 800/400 and the gateway logs a warning.
- The gateway image contains tesseract with English language data for reading scanned PDF pages: about 51 MB more unpacked, 21 MB more to pull. More OCR languages need their language data where the gateway runs (a derived image or a mounted directory with `TESSDATA_PREFIX`) and `capabilities.file_search.parsing.ocr.languages`; developer guide chapter 16, *OCR languages*, shows how for Docker, Kyma and local development. `FILE_SEARCH_OCR=off` switches OCR off, `FILE_SEARCH_VISION=off` vision transcription.
- The npm standalone CLI never reads scanned pages and never transcribes pages with a vision model, whatever the host has installed; it needs no tesseract. PDF files still need `pdftotext` (poppler) on the host and .docx and the other document formats `pandoc`; PowerPoint and Excel files need no tool.
- The file search database gets nullable columns for page numbers (`page_start`, `page_end` on `vector_store_chunks`), for reading files again (`extraction_version` and `ocr_pending` on `vector_store_files` and `fs_reembed_items`, `reextract` on `fs_jobs`) and four page counters on `fs_jobs` (`ocr_pages`, `ocr_skipped_pages`, `vision_pages`, `vision_skipped_pages`, default 0) on the gateway's first start. These change only the catalog; no table is rewritten and no index is built. An install whose database role does not own the file search tables reports file search as unavailable until the migrate CLI (`cli-tools/file-search-migrate.js`, or `FILE_SEARCH_MIGRATION_DATABASE_URL`) has run as the owner.
- File search's vector index: a new install creates a smaller index that also covers embeddings of up to 4,000 dimensions. An upgrade changes no index and starts no build; the existing index stays until you run `rebuild-index` (`cli-tools/file-search-migrate.js rebuild-index`; standalone CLI: `sail-proxy file-search rebuild-index`; `--dry-run` first shows the size and an estimated time). It builds the new index while ingestion and searches go on, then swaps it in; on a large database it takes minutes to hours. Run it before switching on approximate search. It needs the owner's credential, like the migration step; Docker, Kyma and standalone commands are in the developer guide, chapter 16. On Kyma, do not back up, restore or reset the database while it runs; `kyma-db-manager.js` refuses to.
- Upgrading to this version's large-store search changes no index, starts no build and calls no model; vector searches stay exact (`capabilities.file_search.ann.enabled` is `false`); the full-text part of searches over more than `exact_max_chunks` chunks is limited (see Changed). The file search database gets two nullable columns, `context_stopped` on `vector_store_files` and `fs_reembed_items`, on the gateway's first start (catalog only; a non-owner install reports file search as unavailable until the migrate CLI has run as the owner). A configuration without `capabilities.file_search.ann` uses its defaults (`enabled: false`, `exact_max_chunks: 20000`, `min_fraction: 0.05`). Kyma: deploy with `deploy-kyma.js`, which renders the admin's `admin-api-config` ConfigMap again with the new keys. The per-file chunk limit (see Changed) is new; check stores with very small chunks and very large files.
- The upgrade starts no new reading and no model calls: files already ingested keep their chunks (without page numbers), vision transcription stays off unless a store is switched to a vision mode, and PowerPoint and Excel files that failed before stay failed. A store's owner reads its files again with **Re-read Files** after an estimate, or retries the failed Office files. Configurations written before this release have no `capabilities.file_search.parsing` block; the gateway then uses OCR in English and vision off. Kyma: deploy with `deploy-kyma.js` from the new checkout, which renders the admin's `admin-api-config` ConfigMap again from `services/admin/api_config.json`; an old rendered copy applied by hand keeps the old file configuration.
- Upgrading to this version's quota checks on Grounding, its SAP AI Core timeouts and its OpenAI-compatible file and vector store changes needs no step: no database change and no new configuration key. Two behaviours change for users: spend and token quotas now apply to Grounding actions in the Admin Cockpit that start paid work, and deleting a file through the API detaches it from every vector store instead of answering `409 file_in_use` (see Changed).
- Legacy Word `.doc` files: the gateway image contains `antiword` (about 0.5 MB more unpacked, about 130 KB more to pull). `FILE_SEARCH_DOC=off` switches `.doc` reading off in any installation; the npm standalone CLI always has it off. `.doc` files that failed as unsupported before stay failed until a store's owner uses **Re-read Files** or **Retry** on them.
- The file search database gets two tables for the Uploads API (`fs_uploads` and `fs_upload_parts`, which holds the parts until an upload is completed, cancelled or expired), created on the gateway's first start by an owner install. An install whose gateway role does not own the tables reports file search unavailable until the migration step runs as the owner.
- The file search database gets a nullable `expires_at` column on `fs_files` and a small index for file expiry, added on the gateway's first start by an owner install. No file has an expiry at the upgrade, so the index is built over no rows and the pause is negligible. An install whose gateway role does not own the tables reports file search unavailable until the migration step runs as the owner.
- `GET /files` without `limit` now returns up to 10,000 files per page (before, 20); a client that relied on the default of 20 now receives every file in one page.

### Added

- **Teams.** A new **Teams** app in the Admin Cockpit groups users above their keys. A user can belong to several teams, one of them primary. A team has a shared **pool**: one budget for the whole team; an empty field takes the pool profile's value, and empty in both means unlimited. It also has a **member profile**, a default for each member that ranks below the member's own limits and own profile. Its catalog and tool policy intersect with the member's own. Usage is booked to the team the request ran under. Team admins see their teams' members, usage and credentials read-only and cannot create, delete or reset quotas. **Entitlements & Quotas** assigns teams to catalogs and to profiles (as pool profile or member profile). API keys and AWS credentials show their effective team and offer **Change Team**. Usage Analytics has a team scope, **Teams by Cost**, **SAP Billing by Team** and a team usage export. A vector store can be shared with a team. Teams are not part of the npm standalone CLI.
- **API reference.** OpenAPI documents for the gateway, the admin OData and REST APIs and the Ollama facade, with Swagger UI at `/admin/api/docs/` on Docker and Kyma (after signing in to the Admin Cockpit) and at `/docs/` on the standalone CLI (local machine only).
- **Documentation site** with guides for installation, the Admin Cockpit, clients and operations, the API reference and narrated videos, published from this repository to GitHub Pages.
- **Setup scripts with back navigation.** `docker/setup-docker.js` and `kyma/scripts/setup-kyma.js` ask every question first, with **Back**, a jump to any earlier answer and a review before anything is written; secrets are masked in the summary. Run again, they offer the current configuration as defaults and keep, renew or regenerate each secret with a warning. Setup asks for the billing currency and optional CU prices.
- **Connections for the standalone CLI.** `sail-proxy connection add|list|remove|test|models` and `connection model add|remove` manage connections to OpenAI, Azure OpenAI, Anthropic and AWS Bedrock without the Admin Cockpit, kept in `connections.json` in the configuration directory. Secrets come from an environment variable (`--secret-env`) or a hidden prompt. Changes apply at once to a running gateway. Standalone tracks no prices or usage for connections, and every API key sees every connection model.
- **SAP AI Core as a Connection.** An administrator can set the SAP AI Core service key in the Connections app (upload the `.json` file or paste it), with resource group, productive flag and price region, test it and activate it. All gateways then switch to that tenant without a restart; deactivating returns to the environment key. A gateway that already serves a cockpit key keeps it when a new key cannot get a token; a gateway still on the environment key installs the new key anyway and its SAP calls fail until it is fixed, so test before activating. The Model Library and catalogs follow the new tenant. An encrypted last-known copy in Valkey covers a gateway restart while the admin is down; without Valkey, or without your own `VALIDATION_TOKEN_SECRET`, a cold boot during an admin outage uses the environment key. The npm command-line installation is unchanged.
- Usage rows record the SAP tenant. Rows from before are assigned to the environment tenant once. The productive flag and the price region are kept per tenant, and correcting the flag reprices the tenant's last 62 days. Usage Analytics gains an **SAP Tenant** filter (shown when the installation has more than one SAP AI Core tenant) and a **Connection** filter for external spend (administrators see connection titles, other users names and only their own usage), and invoice reconciliation takes a tenant.
- New AWS credentials take the active SAP AI Core region.
- The **Connections** app in the Admin Cockpit (administrators only): define connections to Azure OpenAI, AWS Bedrock, the OpenAI API and the Anthropic API, set and clear credentials in a masked dialog, test a connection, add models from the provider's own model list, set list prices and publish or unpublish models. Prices are entered in the installation currency; an installation billing in USD gets a suggestion from LiteLLM's public price list (a trimmed MIT-licensed snapshot shipped with the admin). The Model Library shows where each model comes from and leaves Connection prices to Connections; Usage Analytics' average cost per request counts SAP requests only.
- **Admin API change for scripts:** `ProviderConnections` is edited through drafts. A plain `POST` creates a draft; scripts that need an active connection in one call post with `"IsActiveEntity": true`, and keys carry `IsActiveEntity` (`ProviderConnections(ID=…,IsActiveEntity=true)`). A key without it (a bare ID) answers 400 on GET and PATCH. Deleting a connection now deletes its models, closes their open prices and deletes its credential.
- Connections registry, the groundwork for sending inference to provider accounts outside SAP AI Core (Azure OpenAI, AWS Bedrock, the OpenAI API, the Anthropic API). Administrators define connections, store each one's credential encrypted, set per-model list prices in the installation billing currency and publish models, through the admin API. A published model appears in the gateway's model lists as `<model>--<connection>`, also while SAP AI Core's model list is unavailable. It is visible only to keys whose entitlement catalog lists it, never through the default catalog.
- Requests to an OpenAI or Azure OpenAI connection model are served by that connection on `/openai/v1/chat/completions` (streaming natively), `/openai/v1/responses` and `/openai/v1/embeddings`, and through the OpenRouter-compatible API. They run through authentication, tool governance, quotas, substitution and the plugins, pseudonymization included, as SAP requests do, and never reach SAP AI Core. Other routes refuse a connection model with a 400 that names the route to use; a connection that is inactive or has no credential answers 503, a model without a list price 409. Usage from a connection is recorded with its connection and upstream model and priced from the model's list price (see Billing).
- Requests to an Anthropic API connection model are served by that connection on `/anthropic/v1/messages`, plain and streaming, through authentication, quotas, substitution and the plugins as for the OpenAI connections. The client's `anthropic-beta` header is passed on; web search is refused with 400 `web_search_not_supported`, and `count_tokens` remains a local estimate. Usage is recorded with its connection and priced from the model's list price.
- Requests to an AWS Bedrock connection model are served by that connection on `/anthropic/v1/messages`, plain and streaming, through authentication, quotas, substitution and the plugins as for the Anthropic API connections. Claude models only. A connection signs in with an access key (optionally with a session token) or a Bedrock API key; newer Claude models need the inference-profile id (for example `us.anthropic.claude-haiku-4-5-20251001-v1:0`), which Fetch models lists. Web search is refused with 400 `web_search_not_supported`, and `count_tokens` remains a local estimate. Usage is recorded with its connection and priced from the model's list price.
- Administrators can test a connection and list its upstream models (`testConnection`, `fetchModels` on the admin API); the gateway calls the provider and answers with a reason code, never the provider's text.
- `GET /anthropic/v1/models` and `/anthropic/v1/models/{model_id}` list the Claude models a key may use, in Anthropic's format. n8n's Anthropic credential test and model list use it, as does the Anthropic SDK's `models.list()`.
- The Usage app's Models tab shows tokens per second for each model: output tokens over the full response time of the period's requests, so for streaming requests it includes the wait before the first token. Table-cell models show no figure.
- The Usage app's Model Performance Details table has an Access column showing Foundation or Deployment, so a model and its deployment-served twin of the same name can be told apart. The CSV export's Model Usage section carries it as `Access Type`, and the Export Data menu has a new Export Model Usage entry.
- The Usage app's Cost Analysis by Model table shows each model's name instead of its raw id, with the same Access column.
- The Admin Cockpit has a new **Grounding** branch for the `file_search` tool. Under **Vector Stores** a user creates stores, attaches or uploads files, watches ingestion and sets an expiry; under **Files** a user uploads, downloads and deletes files and sees where each is attached. It needs a gateway with a file search database and says so when there is none.
- The Grounding branch has a **Jobs** screen: attaching or uploading several files at once runs as one job with its state, progress, failed files and embedding tokens; a job can be cancelled, and its failed files retried. A single failed file can be retried from its store. Finished jobs are kept for 30 days.
- A vector store's new **Test Retrieval** tab shows which passages the `file_search` tool finds in the store for a query, with their files and scores.
- Grounding has an **Administration** screen for administrators: an overview of stores, files, uploaded and stored size, deduplication savings and failed ingestions, and every user's stores, files, failed ingestions, storage and jobs. An administrator can delete any user's store or file and retry a failed ingestion. Other users do not see the entry.
- An administrator can share a vector store they own with all users. A shared store appears in every user's **Vector Stores** list marked **Shared**, with its owner; users can search it, and its search results name the source documents, but they cannot see its file list or change it.
- The Grounding **Files** screen shows how many files your library holds and their total size.
- The Admin Cockpit can be shown in seven languages. A **Language** choice in **Settings** switches the whole cockpit, including the Fiori Elements screens and the configuration form, between English, German, French, Portuguese, Italian, Spanish and Dutch. By default it follows the browser's language; a chosen language belongs to the signed-in user and follows them to every browser they sign in from.
- Dates and numbers in the Admin Cockpit follow the cockpit language, for example `1.234` and `5.10.2026` in German.
- Vector stores can be re-embedded. A store whose embedding model is no longer the configured one is shown as **Outdated** in the Grounding cockpit, and its owner or an administrator can re-embed it in place with the configured model, after an estimate of files, chunks and tokens. The store keeps its id and answers searches with its old vectors until the new ones are complete, then switches in one step. A re-embed runs as a job that can be cancelled, which leaves the store on its previous model, and retried. Administrators see an **Outdated Stores** tile, can filter stores by embedding state, and can re-embed every outdated store of every user in one job.
- A vector store's Details show its embedding model, dimension, generation and embedding state.
- A failed re-embed job lists the files that failed, with their error and number of attempts, 50 at a time; a re-embed of outdated stores also names each file's store.
- MCP naming client entries in the configuration accept **Server names** and a **Tool name pattern**. The gateway already read both, but the configuration refused them. Server names let a client such as opencode, which names an MCP tool `<server>_<tool>`, have its tools governed as MCP tools.
- File search can store the content of uploaded files in an S3 bucket (AWS or S3-compatible): set `capabilities.file_search.blob_storage.backend` to `"s3"`, the bucket, region and prefix under `blob_storage.s3`, and the gateway variables `FILE_SEARCH_S3_ACCESS_KEY_ID` and `FILE_SEARCH_S3_SECRET_ACCESS_KEY`. The gateway reads, writes and deletes only below the prefix, never lists the bucket and sends no request on the bucket itself, so keys limited to the prefix suffice. Every file is read from the storage it was written to, so changing the backend moves nothing and strands nothing. Give every installation its own prefix (or bucket): files with identical content share one object, so two installations under one prefix share objects and one deletes content the other still uses.
- Grounding **Administration** has a **Blob Storage** panel: where file contents are stored, per storage and whether it can be reached, objects awaiting deletion, a **Test S3 Connection** button (it writes and reads back one small fixed probe object below the prefix, which stays there), and a **Blob migration** that moves every file's content to the database or to S3, verified before each switch, with progress, cancel and retry of failed blobs.
- Vector stores can follow their documents' structure. A store's chunking setting is **Static** (fixed windows of tokens, as before) or **Structure**: chunks follow headings, paragraphs, tables, code blocks and PDF pages and carry their heading path. Each store keeps the setting it was created with; the Grounding cockpit's **Create Store** dialog sets it, and `capabilities.file_search.chunking` (`strategy`, `max_chunk_size_tokens`, `chunk_overlap_tokens`, `contextual`) sets the default for new stores (see Changed).
- Contextual chunks: with **Structure**, a store can have a language model write a short context for every chunk before it is embedded, so that search finds passages whose own text does not name what they are about. The model is `capabilities.file_search.contextual.model` (default `gemini-3.5-flash-lite`); the other keys of `capabilities.file_search.contextual` limit the document sent per call, the parallel calls, the time and the tokens one file may spend. A context that cannot be written leaves the chunk searchable without it; jobs show the context tokens and the chunks without context. Search results and citations return the documents' own text and a file download returns the file as uploaded; the contexts are only used to find chunks.
- For stores with **Structure** chunking, the Responses `file_search` tool gives the model the section around each matching passage, up to `capabilities.file_search.parent_sections.max_tokens` (default 1,500), instead of the passage alone; several matches in one section count once. `parent_sections.scope` (`tool`, the default; `all`; `off`) decides where sections are returned; the vector store search API returns passages unless it is `all`.
- **Change Chunking** in the Grounding cockpit changes a store's chunking setting for its owner or an administrator: it shows an estimate of files, chunks, embedding tokens and, for contextual chunks, context tokens, then runs a **Re-chunk** job that reads every file again. The store answers searches with its current chunks until the job has finished and keeps them when the job is cancelled or fails. A re-chunk to a contextual setting is refused (`context_model_unavailable`) when the context model is not available. For a contextual store whose chunks were partly stored without a context, the estimate counts them (`chunks_without_context`) and a re-chunk with the store's own setting writes them.
- File search reads scanned PDFs: pages without a text layer are read by text recognition (tesseract OCR) in the Docker and Kyma installations, in English by default and in the languages set in `capabilities.file_search.parsing.ocr.languages` (each needs its language data installed). OCR reads at most 200 pages of a file; a page it cannot read stays empty and the file is ingested all the same. Text PDFs are read exactly as before.
- File search reads PowerPoint (`.pptx`) and Excel (`.xlsx`) files with a built-in reader: slides with their titles, text, tables and speaker notes; sheets as tables. Hidden slides and sheets are read and marked. A file beyond the reader's limits (for example more than 2,000 slides, 1,000 sheets or 500,000 filled cells) or a password-protected one fails with "Could not read the PowerPoint file" or "Could not read the Excel file" and the reason. `.ppt` and `.xls` stay unsupported.
- File search reads legacy Word files (`.doc`, Word 97–2003) in the Docker and Kyma installations, with `antiword` in the gateway image; a file it cannot read (password-protected, damaged, or not a Word file) fails with "Could not read the Word file". The npm standalone CLI does not read them, and `FILE_SEARCH_DOC=off` switches them off in any installation; such files fail with "legacy .doc files are not supported on this deployment".
- Search results carry page numbers: passages from PDF files name their pages and passages from PowerPoint files their slides, as `pages` (`first`, `last`) on vector store search results, on the Responses `file_search` tool's results and on `file_citation` annotations, and in the **Pages** column of **Test Retrieval**. The field is an addition to the OpenAI shapes and is left out where pages are unknown.
- Vision transcription (opt-in per vector store): a vision model of SAP AI Core reads chosen PDF pages as images and writes out their text, tables included — pages without text, pages with little text and table pages, or all pages. It is off by default and set in **Create Store** and **Change Chunking**, whose estimate shows the pages, tokens and cost as an upper bound. Each page is one model call, repeated whenever the file is read again. Page images are not masked; where pseudonymization is switched on for file search content, the cockpit and the gateway log warn. `capabilities.file_search.parsing.vision` sets the model (default `gemini-3.5-flash-lite`), the default mode for new stores (`off`) and per-file limits.
- File search can search large vector stores approximately, through the vector index: `capabilities.file_search.ann`, off by default. When switched on, only searches over more than `exact_max_chunks` chunks (default 20,000) and at least `min_fraction` of all stored chunks (default 5 %) use the index, and only without an attribute filter, with the index `rebuild-index` builds and on pgvector 0.8 or later; every other search stays exact, and a search for which the index finds too few chunks runs exactly. Approximate search is faster on large stores, but it can return a full list of passages that still misses some of the best-matching ones, and nothing then repeats the search exactly. Run `rebuild-index` first, then measure recall on your own data with the read-only recall probe (developer guide, chapter 16), before switching it on.
- A file whose contexts stopped at the writer's time or token limit is marked **Context incomplete** in its store's file list. A re-chunk with the store's own setting tries a time-limited file once more; a token-limited one is not tried again, since it would spend the same tokens and stop at the same place.
- The Grounding job page shows the PDF pages read with OCR and with a vision model, and the pages each left as they were.
- Grounding **Administration** has **Re-read Files** for any user's store, and an administrator who opens another user's job from the **Jobs** tab sees its page with its failed files.
- The npm standalone CLI has `sail-proxy file-search rebuild-index` (see Deployment).
- **Re-read Files** on a vector store reads again, after an estimate, the files this version reads better (PDF files ingested by an earlier version, and PDF files read where OCR did not run once it does), and queues again the PowerPoint, Excel and Word `.doc` files that failed as unsupported. Files that need no new reading keep their chunks; search keeps the current chunks until the job has finished.
- The files and vector store API follows more of OpenAI's: files carry `status: "processed"` (so the SDKs' wait-for-processing helpers return at once) and `GET /files` honours `?purpose=`; a file batch takes `files` with each file's own `attributes` and `chunking_strategy` instead of `file_ids`; a vector store search takes `query` as a list of up to 10 strings (8,192 characters in total), merged into one ranked list and re-ranked once; `ranking_options.ranker` `"none"` returns results without re-ranking (no re-ranking cost); `ranking_options.hybrid_search` also accepts `rrf_embedding_weight` and `rrf_text_weight`.
- The Grounding **Jobs** screen shows 20 jobs at a time with **More** for the next ones.
- Files can expire, as on OpenAI: an upload takes `expires_after` (`anchor` `created_at`, `seconds` from 3600 to 2592000, sent by the OpenAI SDKs as `expires_after[anchor]` and `expires_after[seconds]`) and the file object then carries `expires_at`. An expired file is gone at once: it is no longer listed, returned, downloaded, searched or shown in its vector stores, and attaching or deleting it answers as for a file that does not exist; the gateway deletes it within minutes as a user delete would, removing it from the owner's vector stores. Files without `expires_after` never expire, and their file objects are unchanged. Any other `expires_after` is refused with `400 invalid_expires_after`.
- OpenAI's Uploads API for the hosted file search (`/openai/v1/uploads`, also under `/openai/api/v1` and `/openrouter/api/v1`): create an upload, add parts, complete it in the part order you give (with an optional `md5` check) or cancel it, as the SDKs' `client.uploads` does. The completed upload is an ordinary file with the same purposes, `expires_after` and size limit as a direct upload. A part is at most 32 MiB with the default file size limit (never more than 48 MiB, below the 50 MB request limit of the Docker and Kyma proxy) instead of OpenAI's 64 MB, so pass the Python SDK's `upload_file_chunked` a `part_size` of at most 32 MB. A larger part up to 50 MB is refused with `413 part_too_large` naming the limit; on Docker and Kyma a request over 50 MB is refused by the proxy with a plain 413. An upload takes at most 1,000 parts, an owner can have at most 10 pending uploads, and a pending upload expires one hour after creation, as on OpenAI.
- The files API accepts uploads with purpose `user_data` as well as `assistants` (both can be added to vector stores), and `GET /files?purpose=` lists the files of either. `GET /files` returns up to 10,000 files per page by default and at most, as OpenAI's does (before, 20 and 100). A file batch takes up to 2,000 files, as OpenAI's does (before, 500); creating a vector store still takes up to 500.

### Changed

- Stored configurations need the `converse` and `converse-stream` hook chains under `hooks.defaults.aws-bedrock`; add them to a configuration stored before this release, or the Bedrock Converse routes run without the default hooks.
- One SAP AI chat path now sends the configured `SAP_AI_RESOURCE_GROUP`; it sent a fixed `default` (the other paths already used it). Installations with another resource group should check it is the intended one.
- The draft of a new AWS credential prefills the region from `SAP_AI_REGION` or the active SAP AI Core key instead of a fixed `us-east-1`.
- The Usage Analytics statistics views now split per SAP tenant: a key used on two tenants has one row for each.
- The gateway, admin and ollama Docker images run on Node.js 24 LTS (`node:24-alpine`); Node.js 20 reached end of life on 2026-04-30. They carry OpenSSL 3.5 or later, both the one bundled in Node and Alpine's system libraries. The standalone CLI still runs on Node.js 20 or later. Rebuild and redeploy the images.
- File search's keyword (full-text) matching now works for natural-language questions: it matches any of the
  question's words except common English and German words, instead of requiring every word. Keyword matches now
  contribute to search results, and the `hybrid_search` weights have an effect. Setting
  `capabilities.file_search.hybrid.lexical_query` to `"all"` restores the previous behaviour.

- File search no longer sorts every chunk of a large vector store, so searches on large stores are faster; the results are unchanged. On a database shared by many stores, a search of a small store can take a few milliseconds longer. Cleaning up the leftovers of a re-embed is cheaper too. The upgrade adds one index on the first start: writes to vector stores pause briefly while it is built (seconds on a database with millions of chunks); searches are not affected.
- File search on a database with few vector stores no longer reads every stored chunk to search a small store: a 2,000-chunk store beside a store of a million chunks is searched in about 10 milliseconds instead of 0.2 to 0.5 seconds. The results are unchanged.
- The full-text part of a search over more than 20,000 chunks (`capabilities.file_search.ann.exact_max_chunks`, whether or not approximate search is on) leaves out the words that more than 5 % of all stored chunks contain, unless every word of the question is that common, and ranks a limited set of matches: on a store of a million chunks, the full-text part of a question with a very common word took several seconds and now takes well under a second. Passages that contain every word of the question are still found first; other full-text matches of such a large search can differ. Searches over fewer chunks are unchanged.
- When file search cannot run, the Grounding cockpit and the `503 file_search_unavailable` answer say why: switched off in the configuration, no database, embedding dimensions outside 1 to 4000, the database not set up or too old to upgrade, or a failed setup. Before, every case said that there was no file search database.
- **Re-read Files** says how many failed PowerPoint, Excel and Word `.doc` files it could not queue again because their upload batch is still being read or was cancelled.
- Writing the contexts of a file that reached its token limit (`contextual.max_input_tokens_per_file`) is not retried by a re-chunk any more; a file that reached its time limit is retried once.
- File search bounds the memory ingestion uses. Cutting a file into structure chunks runs with a heap limit (a fifth of the gateway's memory limit, 256 to 384 MB); a file that needs more fails with "Chunking the file needs more memory than the chunker may use". One file may make at most 21,845 chunks at 1536 embedding dimensions (12,500 at 3072 and 4000), never fewer than a file at the per-file token limit makes at 400 tokens a chunk; a file with more fails with "The file has N chunks, more than the M a file may have at D embedding dimensions. Choose a larger chunk size (max_tokens) or split the file." With the default chunk sizes no file the limits accept reaches it. Files are embedded within a memory budget (a quarter of the gateway's memory limit, 256 MiB to 1 GiB): the largest files wait for each other instead of being held at once. A file that waits too long is put back without counting as an attempt, up to three times, then as a retry; its PDF pages are read again on each round, so under sustained memory pressure vision pages can be paid for more than once. Without the chunker thread, texts over 2 Mi characters (2,097,152) are not chunked on the gateway's main thread but retried later. A plain re-embed now also has a 12-minute embedding deadline per file, as other ingestion has (before, none); a very large file that needed longer fails transiently and is retried.
- Each vector store is searched, and its new files embedded, with the embedding model it was built with. Before, both used the configured model, so changing `capabilities.file_search.embedding_model` silently degraded the search of every existing store. A store whose model is no longer served now answers `409 store_model_unavailable` instead of searching with another model.
- Large files are embedded in requests of at most 256 chunks and about 250,000 tokens instead of a single request.
- A file whose content cannot be read, because its storage cannot be reached or the content is missing, answers `503 blob_storage_unavailable` ("The file content storage is unavailable.") on download and upload. A download of missing content answered `500 blob_missing` before.
- File search requests that wait more than 15 seconds for a database connection answer `503` ("file_search is busy …") instead of waiting until the client gives up. With S3, uploads waiting for S3 can no longer occupy every database connection, so searches and lists keep working while S3 is slow; an upload that waits more than 15 seconds for its turn answers `503 blob_storage_unavailable`.
- With S3 configured, an upload of content that is already stored is written to S3 again and answers like a new upload, including `503 blob_storage_unavailable` while S3 is unreachable; with `blob_storage.backend` `"local"` every upload answers `503`.
- Deleting a file no longer deletes its content at once: content no file uses any more is removed about 15 minutes later by a periodic cleanup, and a new upload of the same content in the meantime keeps it. With S3, a few unused objects can remain after a prefix change (the objects under the previous prefix) or after a gateway crash during an upload or a migration; they always lie under the configured prefix.
- Configuration Management opens a configuration in the form editor by default, and the toggle lists Form before JSON. A configuration the form cannot show, or a window too narrow to show the toggle, still opens in the JSON editor. Saving from the form now stays in the form; before, it returned to the JSON editor.
- In Configuration Management, pressing a configuration opens it and ticking it selects it for the toolbar; the two no longer affect each other. Delete, Duplicate and Activate above the list act only on the ticked configurations. To act on the open configuration, tick it, or use the new Activate and Duplicate in its title bar. Delete is unavailable while any ticked configuration is active, and closing a configuration keeps the ticks.
- Activating the open configuration while it has unsaved changes first asks whether to save or discard them, because activation uses the saved version.
- Duplicating the open configuration from the form view copies its unsaved changes once they pass the schema check; fields that fail are marked and no copy is made.
- A configuration save is refused, with a message in the cockpit language, when the document is not valid JSON, fails validation, or changes the active configuration. Before, such a save was stored.
- Messages about an active configuration no longer say to deactivate it, because there is no Deactivate. They now say to activate another configuration first, or to duplicate the active one and edit the copy.
- For API users: `isActive`, `deployedAt` and `deployedBy` of a configuration can no longer be written through OData; the request is refused with 400. Use the activate action, or rollback, instead. An OData `PUT` on a configuration is refused too; use `PATCH`. Create configurations with the createConfiguration action (an OData POST on the entity is refused with 400). The REST endpoint `PUT /api/admin/api-config` is unchanged.
- Model renames (`substitute_models`) under `openai` and `perplexity` now apply on the OpenAI-compatible chat completions and responses endpoints, the `openai` list first; before, both lists were ignored. As on every other provider, the response and the recorded usage name the model the request was sent to, not the name the client used. The shipped configuration no longer contains the sample renames `GPT-4` → `o1` and `GPT-3.5` → `GPT-4`. If a stored configuration still has them, remove them by creating and activating a configuration without them; otherwise requests for those names are now renamed.
- New vector stores use **Structure** chunking (800 tokens, no overlap) with contextual chunks by default, and the reranker reads a chunk's context together with its text (`capabilities.file_search.hybrid.rerank.input`, default `"context_and_text"`; `"text"` reads the text only). On this project's evaluation set this found the right passage more often than the earlier static 800/400 (recall@5 0.834 instead of 0.807, MRR 0.725 instead of 0.711). Adding files to such a store makes one language-model call per chunk, recorded as `file_search/context` usage of the store's owner. This applies to new installations and to those that use the shipped configuration file; a configuration written before this release keeps static chunking (see Deployment). Existing stores keep their chunking. To restore the earlier default for new stores, set `capabilities.file_search.chunking` to `{"strategy": "static"}` (800/400 without contexts) and activate the configuration.
- A vector store file attached with `chunking_strategy` `auto`, or without one, now reports the strategy that was applied: `{"type": "static", "static": {"max_chunk_size_tokens": 800, "chunk_overlap_tokens": 400}}` by default, as OpenAI reports it, or `{"type": "other"}` in a store with **Structure** chunking. Before, it reported `{"type": "auto"}`.
- A malformed `chunking_strategy` on store creation, file attach or file batches is refused with `400 invalid_request_error`, naming the field: an unknown `type`, `static` without both sizes, sizes that are not whole numbers, `max_chunk_size_tokens` outside 100–4096, or `chunk_overlap_tokens` above half of it. Before, such values were stored and the file was then chunked at 800/400 or failed ingestion.
- Spend and token quotas apply to Grounding actions in the Admin Cockpit that start paid work. Work on a store (attaching files or uploading them into the store, retries, re-embedding, **Change Chunking**, **Re-read Files**, creating a store with files) is checked against the quota of the store's owner, **Test Retrieval** against the quota of the user who searches. A refused action shows "Your usage quota is used up …" in the cockpit language and, when the quota names it, says when the quota resets (in UTC). Actions under Grounding **Administration** are not checked, and work already queued or running always finishes.
- `DELETE /files/{id}` of a file attached to vector stores now detaches it from every store and deletes it in one step, as OpenAI does; before, it answered `409 file_in_use`. `409 file_in_use` remains only for a file that a vector store of another user still uses. A file that was part of a file batch leaves the batch, whose counts then cover the remaining files.
- `ranking_options.ranker` on vector store search and on the Responses `file_search` tool accepts `"auto"`, `"default-2024-11-15"`, the Assistants API's `"default_2024_08_21"` (all three re-rank as before), `"none"` and `null` (not set); any other value is refused with `400 invalid_ranker`. Before, the field was ignored.
- Calls to SAP AI Core for its deployment and model lists, for the access token and for embeddings time out and are tried once more after a dropped connection, a timeout or a 502, 503 or 504 answer: a list, the token or a search's embedding waits at most 10 seconds per attempt, an embedding batch of a file 30 seconds. Before, a list or token call that SAP never answered could wait indefinitely, and the model list the gateway publishes after a configuration change could hang. An embedding whose answer has arrived is never sent twice; chat, contexts, page transcription and re-ranking are not retried. The `/v1/embeddings` route is unchanged.
- The estimate of **Change Chunking** and **Re-read Files** names the vision model that has no price and says to add a price for it in the Model Library.
- Whether a search is large enough for approximate search (`capabilities.file_search.ann`) is checked at most once a minute for the same stores, so a store that was shared or grew within that minute is searched exactly until then.
- The `rebuild-index` preflight (also with `--dry-run`) runs with a 30-second statement and a 2-second lock timeout, counts a never-analysed table on PostgreSQL 13 too, and notes an index built with other `m` or `ef_construction` values than the defaults; the gateway logs the same note at boot. When the preflight times out or another index build holds a lock, `rebuild-index` refuses with a message that says what happened and that nothing was changed, and the second preflight, before the build starts, is bounded too.
- The recall probe (`cli-tools/file-search-recall-probe.js`) detects the index kind itself; `--halfvec` and the new `--no-halfvec` force one. With an INVALID index (a failed build, which searches ignore) it says so and that its approximate figures then come from an exact scan.
- A vector store search with a `max_num_results` outside 1–50, or not a whole number, is refused with 400 `invalid_max_num_results` (`null` counts as absent, so the default applies), as OpenAI and the Responses `file_search` tool do; before, it was silently clamped into that range.

### Removed

- The `mockWhimsicalGerundVerb` plugin is retired. It was the first plugin written for SAIL-PROXY and answered Claude Code's status-word requests without calling a model. Its hook sat on the Claude 3 Haiku override, which is gone as well.
- The shipped configuration no longer contains the `anthropic--claude-3-haiku--deployed` override, its rate-limit delay, or the four match rules only that hook used (`payload:maxTokens512`, `payload:temperature1`, `size:1k-3k`, `system:whimsicalPrompt`). The Claude 3.5 Haiku model ids (`claude-3-5-haiku-20241022` and its Bedrock form) now resolve to the Claude 4.5 Haiku deployment.
- The hook setting `callback.strategy` is removed from the configuration schema. The gateway never read it. A stored configuration that still carries the key keeps running, but validation and the form editor refuse it until the key is deleted in the JSON editor.

### Fixed

- Payload logs redact the Azure `api-key`, `x-amz-security-token` and `x-goog-api-key` headers, as they already did `authorization` and `x-api-key`.
- Prompt caching works for Claude models without their own deployment on the `/anthropic` route and on `/aws-bedrock` `invoke` requests. The gateway dropped the client's `cache_control` breakpoints, so every request paid the full input rate; a repeated prompt prefix is now read from the cache. Breakpoints are cached for 5 minutes. Responses report cache reads and writes, including the `cache_creation` object, and the usage records them. A `supports_prompt_caching: false` override on the model turns this off.
- `sail-proxy opencode` (and any launcher whose client was never started) creates the client's configuration folder. It failed with `ENOENT … opencode.json` when `~/.config/opencode` did not exist yet.
- AWS clients that sign over HTTP/2, such as the AWS SDK for JavaScript with its default settings for Bedrock Runtime, are accepted. They sign the `:authority` header instead of `host`, which the gateway refused as an invalid signature (403).
- `converse-stream` on a deployed model answers. SAP streams those events in a format the gateway's new event-stream framing did not read, so the stream arrived empty.
- The `/anthropic` route answers in Anthropic's format when the first message's content is a list of blocks. On models without a deployment it answered in Bedrock's Converse format instead, which Anthropic clients cannot read.
- The `/aws-bedrock` route serves models without a deployment, through orchestration, as the API reference says. It sent every model to a deployment, so SAP answered 404 "Deployment not found" for every model without a `--deployed` deployment. All four subpaths work for Claude models; other models take `converse` and `converse-stream`. Errors on this path answer in Bedrock's format (`message` and `x-amzn-ErrorType`), which the AWS SDKs read.
- Tool calls work on the `/anthropic` route for models served through orchestration (models without a `--deployed` deployment). The gateway dropped the `tool_use` and `tool_result` blocks of earlier turns, so SAP refused the turn after the first tool call ("Assistant message has neither text nor tool_use blocks."). Agents such as n8n's AI Agent failed on their second step. Images reach these models too; before, the gateway dropped them and the model answered as if there were none.
- The `/aws-bedrock` streaming subpaths (`invoke-with-response-stream`, `converse-stream`) answer in AWS's binary event stream (`application/vnd.amazon.eventstream`), as Bedrock does, instead of server-sent events. Claude Code 2.1.308 and later refused the old streams ("expected application/vnd.amazon.eventstream"), and boto3 and the AWS SDKs could not read them. `converse-stream` now sends Converse events (`messageStart`, `contentBlockDelta`, `messageStop`, `metadata` and so on) also for models whose Converse stream the gateway emulates. An error after the stream has started is an exception frame (for example `throttlingException`); an error before it is the HTTP status with a JSON body.
- `sail-proxy claude` sets Claude Code's model and its Opus, Sonnet and Haiku defaults to the newest Claude models the gateway lists. Current Claude Code versions default to a model SAP AI Core does not serve, so the first prompt failed. A `--model` you pass, or a model variable you exported, takes precedence.
- `sail-proxy claude` points Claude Code at the gateway's `/anthropic` route. Version 0.10.0 sent it to the gateway root, which answered 404 on `/v1/messages`.
- The Docker and Kyma nginx lets the `x-goog-api-key` header of the Gemini SDK through to the gateway. Gemini CLI behind the nginx used to get the sign-in redirect.
- Streaming requests that fail before any answer arrives, such as a prompt longer than the model's context window, now get a proper error with its HTTP status in the format the client's API uses (Anthropic, OpenAI or Gemini). Before, the client received an empty streamed reply. Claude Code can now compact the conversation instead of reporting that the streaming response ended without data. A failure after the answer has started ends the stream with a single error event.
- The Anthropic route answers errors in Anthropic's format, streaming or not, and an unknown model with 404.
- Embedding requests stay under SAP's 300,000-token request limit. A file of a few hundred dense chunks no longer fails ingestion with "maximum request size is 300000 tokens".
- Usage Analytics answered an error for every user who is not an administrator (on PostgreSQL and SQLite alike); it now shows their own usage, and only their own.
- Opening an API configuration shows its status, checksum and validation messages again, in both the form and the JSON view; Duplicate keeps unsaved edits; switching quickly between configurations always shows the last one.
- In Configuration Management, opening one configuration and ticking others no longer makes the toolbar act on the wrong one. Before, Delete could remove the open configuration instead of the ticked ones, Activate activated a ticked configuration while another stayed open, Duplicate copied the open configuration's unsaved text into another configuration's copy, Save refused to save the open configuration because a ticked one was active, and Delete was offered for several ticked configurations even when one of them was active.
- After Activate or Rollback, the open configuration turns read-only or editable at once. Before, it kept the state it was opened with until it was opened again.
- Saving a configuration updates its checksum, validity and validation messages, and the detail shows the new values without reopening. Before, they kept the values from when the configuration was created. Activation stores its validation result too.
- A refused configuration save shows the reason. Before, it reported "Configuration saved successfully".
- If a filter hides the open configuration, Save says so. Before, it claimed the configuration was active.
- An empty upstream Bedrock stream now returns 502 instead of a made-up reply.
- The Ollama-compatible service no longer fails a non-streaming completion that takes more than 10 seconds; it now waits up to two minutes, adjustable with `REQUEST_TIMEOUT`.
- The Ollama-compatible service answers an empty `/api/generate` prompt with Ollama's empty load response instead of sending an empty message to the model.
- In the Usage app, the average response time of a model, provider or user that has both API-key and AWS-credential traffic is now weighted by request count; before, the two sources' averages were averaged, so one source's lone request counted as much as the other's thousand.
- In the Usage app, a model that has no pricing row, such as a deployment-served `<model>--deployed` twin, is now shown under its Model Library name instead of its raw id in the Most Used Model tile and the Models table.
- Configuration Management showed every configuration as valid; an invalid configuration is now shown as invalid.
- The cost chart in Usage Analytics labels its slices as percentages instead of fractions.
- Configuration Management showed German dates with day and month swapped.
- Query rewriting for file search (`capabilities.file_search.rewrite_query`) failed on every search with the shipped rewrite model `gpt-5-mini`, which refuses a `temperature`, and searched with the original query without saying so. It now rewrites; a rewrite that fails is logged as a warning.
- A file whose ingestion was put back for lack of memory kept no count of it when the database was busy or the gateway stopping in between, so it could be put back more often than the three times allowed; the count now survives.
- The npm standalone CLI answered 401 to every Files, Vector Stores and Responses `file_search` call made with its own API keys; they now work. All API keys of a standalone gateway share one file-search owner, so they see the same files and vector stores.
